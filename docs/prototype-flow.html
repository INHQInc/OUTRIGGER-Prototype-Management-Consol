When something changes

How it's noticed, what fires, and what clears it

Nothing is ever alerted. Everything is recomputed.

There is no event bus, no webhook, no notification queue. Every alert, every step dot and the "next action" are derived on each read from the same handful of ground-truth inputs. A change doesn't fire anything — it changes an input, and the next render draws a different picture. That's why the board, the tabs and the chip can never disagree.

What the flows can't show yet

Three answers turn the dashed paths solid

Every solid path above is traced from the code. The dashed ones are undecided — drawn as branches rather than guessed at.

  1. Where does type 1 end?

    The two dashed terminals in its chart: does "live on the site as an injection" finish it, or does it also graduate into production code through Handoff?

  2. What opens type 1's Brief gate?

    isBriefComplete demands a primary metric globally. For a type with no experiment the bar could be change + target pages, change alone, or a hand-checked analytics outcome.

  3. Is Handoff real for type 3?

    If yes, the red branch disappears and the stage resolver stops special-casing external. If no, the drag onto Handoff should be refused with a reason rather than accepted and reverted.

Answer those and the change is mechanical: a third buildMode, a per-type Brief rule, a per-type na map across the five steps, and one correction to the stage resolver.
